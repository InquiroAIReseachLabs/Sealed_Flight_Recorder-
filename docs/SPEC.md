## B1. SPEC

### B1.1 Product
- Name: **Sealed Flight Record**. Binary: `sfr`. Record file extension: `.sfr` (JSON). Report: `<name>.sfr.md` (Markdown).
- Purpose: after a PX4 flight, produce a signed, self-verifying record of the configuration that flew, the readiness rule results, and the operator, failsafe, and transition events, so anyone holding the signer's public key can later check that none of it has changed since it was sealed. The check does not show that the data was accurate when it was sealed (README, "What a record proves").
- Runs offline on Linux x86_64, aarch64, and 32-bit ARMv7 (hard-float). No network at runtime, ever.
- Contains no AI, no randomness in sealing, and no telemetry.

### B1.2 Workspace
- `crates/sfr-core`: the engine (ingest, events, rules, record, Merkle, signing, verify). No I/O beyond reading provided byte streams; no networking; `#![forbid(unsafe_code)]`. Cryptography comes from one backend on every target: `sha2`, `ed25519-dalek`, and `blake3` (B1.10 Crypto).
- `crates/sfr`: the CLI. Thin wrapper over `sfr-core`. Statically linked; never loads a shared library.
- `crates/sfr-wasm`: browser build of `sfr-core` for the sandbox. Thin wrapper. Evaluation only. It uses the same crypto crates as `sfr`, so its records match the CLI's byte for byte.
- `crates/sfr-pkcs11-helper`: signs one payload with an Ed25519 key held in a PKCS#11 v3.0 token or HSM (CKM_EDDSA). It runs as a separate process because a static musl binary cannot load a vendor module (`dlopen` fails with "Dynamic loading not supported"). It is the only dynamically linked artifact and is never needed for evaluation.
- `fuzz/`: cargo-fuzz targets.
- `site/`: static sandbox page (HTML, CSS, JS that loads `sfr-wasm`). No third-party scripts, no analytics, no CDN calls.
- `scripts/`: demo, benchmark, README-number regeneration, release.
- `testdata/`: golden logs with license notices, expected records.
- `docs/`: SPEC, THREAT_MODEL, RECORD_FORMAT, RULES, INTEGRATION_NOTES.
- Pinned toolchain (`rust-toolchain.toml`). All builds `--locked`.

### B1.3 Commands

| Command | Behavior |
|---|---|
| `sfr keygen --evaluation-only --out <dir>` | Creates an evaluation Ed25519 key pair (`sfr.key`, `sfr.pub`) from a 32-byte seed from the operating system's CSPRNG. Private key file mode 0600. Refuses to overwrite existing files. Prints the public key fingerprint and EVALUATION KEY. Without `--evaluation-only` it exits 4 and names the hardware key options. |
| `sfr keygen --tpm-sealed --out <dir> [--tpm-parent <handle>] [--tpm-pcrs <bank:list>]` | Generates the Ed25519 seed from the operating system's CSPRNG and seals it to this machine's TPM 2.0 through tpm2-tools (object attributes `fixedtpm\|fixedparent`, optional PCR policy; parent defaults to the persistent storage key `0x81000001`). Writes `sfr.tpm.pub` and `sfr.tpm.priv` (sealed blobs that no other TPM can load), `sfr.tpm.conf` (the parent handle and PCR selection), and `sfr.pub`; before writing, it unseals the seed once and checks the round trip. The seed never touches disk; it reaches the TPM through a pipe (`tpm2_create -i -`). PKCS#11 keys are generated inside the token with the token's own tools (CKM_EC_EDWARDS_KEY_PAIR_GEN, CKA_SENSITIVE true, CKA_EXTRACTABLE false); `docs/INTEGRATION_NOTES.md` gives the commands. |
| `sfr seal <flight.ulg> --rules <rules.toml> --baseline <baseline.params> <key source> [--cert <signer.pem>] [--chain <intermediates.pem>] [--out <dir>] [--seal-time <RFC3339>] [--dry-run]` | Parses the log, extracts configuration and events, runs rules, builds the record, Merkle tree, and signature; writes `<name>.sfr` and `<name>.sfr.md`. The key source is exactly one of: `--key-uri 'pkcs11:<RFC 7512 path>?module-path=<module.so>&pin-source=<file:PATH\|env:VAR>'` (custody `pkcs11-token`: the signature is made inside the token by `sfr-pkcs11-helper`; `pin-value` is refused; see the hardware token caveat below); `--key-uri tpm-sealed:<dir>` (custody `tpm-sealed`: the seed is unsealed into memory for one signature, then zeroized); `--key <sfr.key> --evaluation-only` (custody `file-evaluation`; evaluation only, never for operational records). `--cert` embeds the signer's X.509 certificate (RFC 8410 Ed25519 key), which must hold the signing key (else exit 4, nothing written); `--chain` embeds intermediates. Both are stored in the seal leaf as standard base64 of the DER, so the signature covers them. Before writing anything, `seal` verifies the signature against the signing public key; a mismatch writes nothing and exits 4. `--dry-run` runs everything except signing and writing, and prints the results table. `--seal-time` fixes the seal timestamp for deterministic output. |
| `sfr verify <record.sfr> (--pubkey <sfr.pub> \| --trust-anchor <ca.pem> ([--crl <crl.der>]... \| --no-crl-check)) [--ulog <flight.ulg>] (--report <name.sfr.md> \| --no-report) [--allow-evaluation-key] [--require-hardware-key] [--at <RFC3339>]` | **Trust:** with `--pubkey`, the record must be signed by that key. With `--trust-anchor`, the embedded signer certificate must chain to the anchor offline, carry the sfr record-signing extended key usage (`2.25.182460915354635260549596502533646383540`, and not also code signing, TLS server authentication or any usage) and keyUsage digitalSignature, be valid at the verification time (the verifier's clock, or the time given with `--at <RFC3339>`; never the record's seal time, which is the sealer's claim), not be revoked by any supplied CRL (a listed certificate counts as revoked whatever its revocation date, since the seal time is a claim), and verify the record signature with its own key. **CRLs:** every CRL given is read, in any order; for each issuer, the CRL with the highest `cRLNumber` (RFC 5280 section 5.2.3) is its current CRL and the rest are set aside, and two different CRLs of one issuer with the same highest number are refused. Every issuer of the signer certificate and of the intermediates must have a current CRL, a CRL of another issuer counts for nothing, and a current CRL whose `nextUpdate` has passed by the verifier's clock, or whose `thisUpdate` is more than 300 seconds ahead of it, fails. Each CRL used is printed with its issuer, number, `thisUpdate` and `nextUpdate`. `--no-crl-check` skips revocation entirely, prints a warning, and the output says revocation was not checked; it excludes `--crl`. `--pubkey` and `--trust-anchor` exclude each other; `--crl` needs `--trust-anchor`. Given neither, verify checks nothing, prints `Integrity: NOT CHECKED (no trusted key given)` with the key fingerprint and custody the record names, marked as unproven, and exits 4; it never prints `Integrity: VERIFIED` unless the signature checked against a supplied key or a chain to a supplied anchor. Every verify prints the key fingerprint and the custody: `custody   unattested (declared pkcs11-token)` (the sealer wrote that string; a key file can say it too) unless the signer certificate chains to a supplied anchor, then `attested by certificate chain to the trust anchor <sha256> (declared pkcs11-token)`; what a chain attests is only as much as the CA's issuing practice, which `sfr` cannot see. A record that declares custody `file-evaluation` prints EVALUATION KEY first and, although its signature verifies, is `Integrity: REFUSED` (exit 1) unless `--allow-evaluation-key` is given. `--require-hardware-key` means custody attested by a chain, not declared: it refuses every record under `--pubkey`, and under `--trust-anchor` refuses a declared `file-evaluation`. The output names the custody and the crypto module. **Time:** verify prints the seal time labelled `claimed`, and refuses a claimed seal time more than 300 seconds (the stated clock skew allowance) after the verification time, which is the verifier's clock or `--at`; with `--trust-anchor` it prints which time judged the certificates. **Standalone:** recomputes every leaf and the Merkle root from the record, checks the signature, and checks that the overall status matches the results. **Report:** once the record verifies, verify renders its report from the record and requires the report named by `--report`, or else `<name>.sfr.md` beside `<name>.sfr` when present, to be byte-identical; a difference is an integrity failure (exit 1) that names the first differing line, and so is a missing report, unless `--no-report` is given, which verifies the record alone, prints a notice (on standard error, and as `report    NOT CHECKED` in the output) and excludes `--report`. **Deep (with `--ulog`):** additionally re-hashes the log, re-parses it, replays the embedded rules and baseline, and requires byte-identical results, configuration, and events. On failure, names the first mismatch: leaf index and kind, event sequence number and field, parameter name with sealed and found values, or "log digest mismatch". |
| `sfr pubkey --key-uri (pkcs11:... \| tpm-sealed:<dir>)` | Prints the hardware key's public half as the PEM `sfr verify --pubkey` reads, with its custody, label and fingerprint on a comment line. For `pkcs11:` the helper reads it from the token (`CKA_EC_POINT`); for `tpm-sealed:` the seed is unsealed and checked against the directory's `sfr.pub`. |

Every command supports `--json` for machine-readable output. `sfr --version` prints the tool version and the crypto crates with their crate versions. No command output claims that `sfr` itself holds any compliance status (B1.12).

**Hardware token caveat.** `sfr` needs a token that signs with Ed25519 (`CKM_EDDSA`, pure Ed25519) and checks nothing else about it: not whether its private key can be exported, how the token was made, or any approval it holds. Choosing a token whose key cannot leave it is the operator's decision. `seal` takes no token certificate number and records none; `token_cmvp_certificate` is always null. In `tpm-sealed` the TPM performs no Ed25519 operation (no shipping TPM implements EdDSA); it protects the seed at rest, and the signature is made in `sfr`.

### B1.4 Exit codes
| Code | Meaning |
|---|---|
| 0 | Seal: status PASS or WARN (every rule PASS, WARN or N/A, and the log has an armed flight). Verify: VERIFIED. |
| 1 | Seal: status FAIL (one or more rules FAIL) or NO ARMED FLIGHT (the log has no ARM and no DISARM); the record is still written. Verify: verification failed. |
| 2 | Required topic missing from the log (record written with status FAIL and the missing topic named). |
| 3 | Malformed or truncated input file (log, rules, or baseline), including a log with no data records and an input over a limit (Input limits below); the message names the file and the byte offset or line, except as Input limits below says. |
| 4 | Usage, key, or file I/O error, including a key file or public key over its limit, a missing `--evaluation-only`, a hardware key source that fails, a signature that does not verify against the signing key, and a rules file that lists more than 64 sealed topics. |

#### Input limits

Every input except the log's total size is bounded by the limits below, and an input over a limit is refused, never truncated. A message for a count or a size reads `... exceeds the input limit of N <unit> (SPEC B1.4)`; a message for a name, version, or length rule ends with a parenthesis that states the rule and cites SPEC B1.4. `seal` names the byte offset (log) or line (rules file, baseline) where it met the limit, except for exactly these, which name the file only: three counts (parameters at log start, `failsafe_flags` flag fields, events), the file sizes, and TOML dotted-key depth. `seal` exits 3 for the log, the rules file, and the baseline, including a log whose record would be over the record limit (`seal --dry-run` writes no record and does not apply that limit), and 4 for the key file. `verify` exits 4 for the public key and reports any limit in the record or in the `--ulog` log as its first mismatch (exit 1). `docs/LIMITS.md` gives the reason for each limit.

| Input | Limit |
|---|---|
| Log: ULog file format version | 0 or 1 |
| Log: format nesting | 8 levels of nested types below a subscribed format |
| Log: one flattened format | 65,535 bytes and 65,535 fields; array length 1 to 65,535 |
| Log: field definitions across all formats | 1,000,000 (a format with no fields counts as one) |
| Log: format name, field name, field type name | 255 bytes |
| Log: subscriptions | 4,096 |
| Log: flattened fields across all subscriptions | 1,000,000, counted per subscription |
| Log: flattened field names, summed once per distinct subscribed format | 16 MiB (16,777,216 bytes) |
| Log: flattened field name (with its nested prefixes and `[i]` index), subscription name | 255 bytes |
| Log: parameter name | 1 to 16 letters, digits, `_` |
| Log: parameters at log start | 65,536 |
| Log: `failsafe_flags` flag fields | 256 |
| Log: events (B1.5) | 100,000 |
| Rules file, baseline, key file, public key | 16 MiB (16,777,216 bytes) each |
| Rules: `required_topics.topics`, `parameters.ignore`, `watched_parameters.names`, `payload_commands.ids`, `authorized_sources.sources` | 256 entries each |
| Rules: `sealed_topics.topics` | 64 entries; more is a usage error (exit 4) |
| Rules: watched parameter name | 1 to 64 letters, digits, `_` |
| Rules: payload command id; source system id; source component id | 0 to 4,294,967,295; 0 to 255; 0 to 65,535 (`vehicle_command.source_component` is 16 bits in PX4 v1.17) |
| Rules: topic name | 1 to 64 lowercase letters, digits, `_` |
| Rules: parameter name pattern | 1 to 64 letters, digits, `_`, `*`, with at most 8 `*` |
| Rules: TOML nesting and dotted keys | 80 levels (the limit of the `toml` parser) |
| Baseline: parameters | 65,536 |
| Record (`seal` output, `verify` input) | 512 MiB (536,870,912 bytes); JSON with at most 64 nested arrays and objects |

The log has no size limit. It is read once, as a stream. The reader keeps format definitions, subscriptions, one flattened layout per distinct subscribed format (shared by its subscriptions), and the parameters at log start, each bounded by the limits above, and the data records the events and rules use (for example `vehicle_status`, `failsafe_flags`, commands and acks, warning messages, and data-section parameter records); it hashes and drops every other record. The number of kept data records has no limit, so memory grows with them: a log made mostly of them needs memory in proportion to its size. The detail cap limits output, not input: R4, R5, R6, X2, and X3 list at most 1,000 `detail` lines, then one line `and N more; ...` that says where the rest are counted (the events, or for X3 its sample count). R3 lists every differing parameter (B1.6), so at most the two parameter limits together.

### B1.5 What is extracted from the log

Supported: PX4 v1.14 through v1.17 ULog. `seal` refuses a log whose `ver_sw_release` is outside v1.14 to v1.17, or cannot be read, with exit 4 and nothing written, unless given `--allow-untested-version`; then it warns on stderr, records `seal.allow_untested_version` true, and the report says so. Exact topic and field names per version come from the PX4 message definitions of that version and are checked against the golden logs, never taken from memory.

- **Log identity:** SHA-256 of the raw file bytes, which is the digest the seal rests on, and BLAKE3 of the same bytes as an index for finding the file (it adds no security); file size; firmware version and git hash from the ULog info messages `ver_sw_release` and `ver_sw`; vehicle type from `vehicle_status.system_type` and `is_vtol`.
- **`vtol_type`** (in the log identity's vehicle): when the vehicle is VTOL (`vehicle_status.is_vtol` true on some sample, as for R4 and R6), parameter `VT_TYPE` from the parameters at log start, recorded as its raw integer and its PX4 name: `0` tailsitter, `1` tiltrotor, `2` standard (the same in PX4 v1.14 and v1.17). Any other value is `unknown(<n>)`, never guessed; a log without an int32 `VT_TYPE` records value null and name `unknown`. Null for a vehicle that is not VTOL. `vehicle_status.system_type` uses MAVLink's MAV_TYPE numbering and is not mapped through `VT_TYPE`.
- **Configuration:** the full parameter set at log start (the 'P' records before the first subscription) as a sorted key-to-value map, each value typed int32 or float32; firmware version. R3 compares the parameters in effect at each ARM, which data-section 'P' records before it change (B1.6).
- **Field types:** every field a rule or an event reads must have the type the PX4 message definitions of v1.14 to v1.17 give it; a field with another type, in any subscription of its topic with data records, is not read, and each rule that needs it fails as `cannot evaluate` (B1.6). A format record that names one field twice makes the log malformed (exit 3).
- **Instances:** every `vehicle_status` instance with data records is read; its events carry its instance number, and the record states the instance count (`log.vehicle_status_instances`).
- **Skipped messages:** records of an unknown type, data records without a subscription, and regions skipped to reach an appended-data offset are counted in `log.skipped`; the report says `sealed with N skipped messages`.
- **Events (the timeline), each with a sequence number, boot-time microseconds, UTC microseconds when GPS time is available, and its source (topic, instance, message index):** UTC comes only from the first GPS sample (`vehicle_gps_position`, else `sensor_gps` instance 0) with `fix_type` of at least 2 and a nonzero `time_utc_usec`, never from `boot_time_utc_us` or a host clock.
  - ARM, DISARM: edges of `vehicle_status.arming_state == 2`, with the reason decoded from PX4's events enum. A log that starts armed reports ARM at its first sample, marked `initial`.
  - NAV_STATE_CHANGE (old, new): edges of `vehicle_status.nav_state`, with per-version names; the first sample is reported with `old` null.
  - FAILSAFE_SET, FAILSAFE_CLEAR (flag name; from `failsafe_flags`): edges of `vehicle_status.failsafe`. Each edge names the `failsafe_flags` booleans (and `battery_warning` above 0) that are true at that moment and are either required by the current `nav_state` (the flag's `mode_req_*` bit is set) or were not true at the most recent ARM (the latest `failsafe_flags` sample at or before that ARM; when there is none, or no ARM precedes the edge, the sample with the earliest timestamp); one event per named flag, or one event with flag `unattributed`. A log that starts in failsafe reports FAILSAFE_SET at its first sample, marked `initial`.
  - COMMAND (command id, category, source system and component, result from the matching `vehicle_command_ack`, or `NO_ACK`): the category is `PAYLOAD` when the command id is in the rules file's `[payload_commands]` list, otherwise `GENERAL`. Every COMMAND event records its source system and component. the matching ack is the earliest unused ack with the same command id, a timestamp not before the command's and before the next identical command from the same source, and target system and component equal to the command's source; a final result is preferred over IN_PROGRESS.
  - VTOL_TRANSITION_START, VTOL_TRANSITION_END, VTOL_TRANSITION_ABORT (direction): from the VTOL state derived from `vehicle_status` (in transition to fixed wing, in transition to multicopter, fixed wing, multicopter). START when a transition state is entered; END on transition-to-fixed-wing then fixed wing, or transition-to-multicopter then multicopter; ABORT when a transition state is left any other way. A quadchute (fixed wing straight to multicopter) is not a transition; R4 reports it.
  - QUADCHUTE (`vtol_fixed_wing_system_failure` true, false, or null when not logged): the VTOL state goes from fixed wing straight to multicopter without a transition state; the flag is the `failsafe_flags` value at that moment. R6 does not count it; R4 fails on it in flight (B1.6).
  - A `failsafe_flags` value "at that moment" (FAILSAFE_*, QUADCHUTE) comes from the latest `failsafe_flags` sample whose timestamp is at or before the `vehicle_status` sample's, in timestamp order whatever the file order, and among samples with that timestamp the one later in the file; with no such sample the flag is null, and a FAILSAFE edge is `unattributed`.
  - Edges (ARM, DISARM, NAV_STATE_CHANGE, FAILSAFE_*, VTOL_*, QUADCHUTE) compare consecutive `vehicle_status` samples in file order; the timeline then orders the events as below.
  - PARAM_CHANGED_IN_FLIGHT (name, old, new): a data-section 'P' record whose value differs from the last known value of that parameter, between ARM and DISARM: after the arming `vehicle_status` row (ARM time < its time, or its time equal to the ARM time and the record later in the file than the arming row) and at or before the DISARM time; its time is the last data timestamp before it. Firmware-written changes count like any other.
  - LOG_MESSAGE (flight stack messages at warning level or above): 'L' and 'C' records at levels 0 to 4 (emergency to warning), text kept verbatim. PX4 events (the `event` topic) are not decoded in v1.
  - LOG_DROPOUT (duration): an 'O' record, in milliseconds; its time is the last data timestamp before it.
- **Sealed topic digests:** for each topic the rules file lists in `[sealed_topics]` and each instance (`multi_id`) the log subscribes, one entry: `topic`, `multi_id`; `format_sha256`, the SHA-256 of the payload of the 'F' record that defines the topic's format, exactly as stored (`<name>:<fields>`), the latest one before the instance's first subscription; `message_count`, its data records; `first_timestamp_us` and `last_timestamp_us`, the timestamp field of its first and last data record in file order (null with no data record); and `data_sha256`, the SHA-256 over its data records in file order, each contributing its payload length as an 8-byte little-endian integer followed by the payload bytes after the message id (the message id is per file and is not stable across logs). Computed while the log streams; no data record is kept. `docs/RECORD_FORMAT.md` gives the byte layout. A sealed topic needs no knowledge of its message structure; ULog is self-describing. The format digest covers the topic's own 'F' record only, not the 'F' records of the nested types it uses.
- **Event ordering** is deterministic: boot time, then topic name, then instance id, then message index. Records without a topic use the names `ulog.logging`, `ulog.parameter`, and `ulog.dropout`. Several events from one source message keep this order: ARM or DISARM; NAV_STATE_CHANGE; FAILSAFE_SET or FAILSAFE_CLEAR, one per flag, by flag name in byte order; VTOL_TRANSITION_END, VTOL_TRANSITION_ABORT, or QUADCHUTE; VTOL_TRANSITION_START. Sequence numbers start at 0. The message index counts from 0: for a topic, the data record's position among that topic instance's data records; for `ulog.parameter`, among all 'P' records in the file, definitions section included; for `ulog.logging`, among all 'L' and 'C' records; for `ulog.dropout`, among all 'O' records.
- **Multi-instance topics** are filtered to the active instance where PX4 records one (used by optional estimator rules only).

### B1.6 Rules

Rules file format: TOML (Rust TOML tooling is actively maintained; the common Rust YAML crate is not). The rules file and baseline are embedded in the record so deep verify needs only the log.

**Core rules, on by default:**
| Id | Rule | PASS / FAIL / N/A |
|---|---|---|
| R1 | Required topics present (the rules file lists them, every sealed topic is required too, and with `[authorized_sources]` so is `vehicle_command`), each with at least one data record, plus the `vehicle_status` and `failsafe_flags` fields the core rules read and, with `[authorized_sources]`, the `vehicle_command` fields R7 reads (`command`, `source_system`, `source_component`), in every `vehicle_command` subscription that has data | FAIL names each missing topic or `topic.field`; exit 2 |
| R2 | Firmware the log states matches baseline; the line says the version is self-reported and gives the baseline file's SHA-256 as operator-supplied | FAIL shows expected and found |
| R3 | Parameters in effect at every ARM match baseline, excluding the ignore list; none changes in flight. The line gives the ignore list, the number of differences it suppressed, and the baseline file's SHA-256 as operator-supplied. A pattern that matches every name is refused unless `seal --allow-ignore-all` is given, which the record states | FAIL lists every differing parameter with baseline and flown values; WARN counts the parameters changed in flight |
| R4 | No failsafe raised during flight, on any `vehicle_status` instance: `vehicle_status.failsafe` never true from ARM through the `vehicle_status` sample that disarms, no quadchute (fixed wing straight to multicopter, B1.5) in that window, and no `failsafe_flags` flag that the `nav_state` in effect requires (its `mode_req_*` bit) true in that window. The quadchute check reads the VTOL state fields (`in_transition_mode`, `in_transition_to_fw`, `vehicle_type`) only when the vehicle is VTOL, that is when `vehicle_status.is_vtol` is true on some sample; an absent `vehicle_status`, or an absent `is_vtol` field, means not VTOL here, and R1 carries that failure | FAIL lists each flag and time, each quadchute, and each required flag; WARN names every other `failsafe_flags` flag true in flight; N/A with no armed flight |
| R5 | Arm and disarm consistency, on every `vehicle_status` instance: every ARM has a DISARM, log does not end armed | FAIL names the unmatched event; N/A with no ARM and no DISARM (no armed flight) |
| R6 | VTOL transitions completed: every start has an end, none aborted. On a VTOL vehicle the first detail line states the `vtol_type` (B1.5) | N/A if the vehicle is not VTOL; FAIL when `system_type` is a VTOL MAV_TYPE but `is_vtol` is false on every sample |

**Optional rule R7, authorized command sources** (off by default; only the operator knows their own system and component ids, so `examples/rules.extended.toml` carries a commented example):
| Id | Rule | PASS / FAIL / N/A |
|---|---|---|
| R7 | Every COMMAND event came from a source listed in `[authorized_sources]`; with `category`, only commands of that category are checked | FAIL names each unauthorized event (sequence number, command, category, source system and component); FAIL when its input is missing: no `vehicle_command` data record, one of the three fields absent, or one of them with a type other than PX4's (a log with no commands is no evidence of authorized ones); PASS when commands are present and none in scope is unauthorized, stating the scope, the number of commands it excluded, and that source ids are self-reported by the sender; N/A when the rules file has no `[authorized_sources]` |

**Optional rules file sections**, each absent by default unless noted:
- `[watched_parameters] names = [...]`: parameter names shown apart for presentation. R3 compares them exactly like every other parameter, with no extra rule and no double counting; a watched name the ignore list matches is a rules file error. The record lists them in `config.watched_parameters`, and the results table and report show them in a "Transition tuning" section with the `vtol_type`, each with its baseline and flown values and MATCH or DIFF. `examples/rules.default.toml` watches ten VTOL transition parameters, each confirmed in PX4 v1.14 and v1.17.
- `[sealed_topics] topics = [...]`: uORB topic names, at most 64. Each is required (R1) and digested (B1.5).
- `[payload_commands] ids = [...]`: command ids whose COMMAND events are `PAYLOAD`. `examples/rules.default.toml` lists the actuator, servo, gripper, winch, payload deploy, camera trigger, and image capture commands, each id and name taken from PX4's `VehicleCommand.msg` for v1.14 and v1.17; flight termination and parachute commands are not in it.
- `[authorized_sources]`: `sources = [{ system = <id>, component = <id> }, ...]` and an optional `category = "PAYLOAD"` or `"GENERAL"`; enables R7.

**Optional example rules** (shipped in `examples/rules.extended.toml`, off by default, thresholds labeled "set by your flight-test lead"): minimum battery, GPS fix at arm, estimator fault flags, accelerometer clipping and vibration, total dropout time.

**Time windows.** Each rule and in-flight event reads the log over this window. "ARM" and "DISARM" are the boot times of the `vehicle_status` samples where `arming_state` becomes and stops being armed (B1.5); an interval still open at the end of the log runs to its end. Every armed interval counts.

| Rule or event | Window |
|---|---|
| R1 | the whole log |
| R2 | none: the firmware identity (B1.5) |
| R3 | the parameters in effect at each ARM, and PARAM_CHANGED_IN_FLIGHT events |
| R4 | `vehicle_status` samples with ARM ≤ t ≤ DISARM: from the ARM sample through the sample that disarms; a quadchute is judged on the sample where the VTOL state becomes multicopter |
| R5, R6 | the whole log (every ARM, DISARM, and VTOL event) |
| R7 | the whole log (every COMMAND event) |
| X1 (battery), X3 (estimator faults), X4 (vibration and clipping) | samples of that topic with ARM ≤ t < DISARM; X4 compares consecutive samples only within one armed interval |
| X2 (GPS fix at arm) | at each ARM: the latest GPS sample with a timestamp at or before it |
| X5 (dropouts) | the whole log |
| PARAM_CHANGED_IN_FLIGHT (B1.5) | records with ARM < t ≤ DISARM, or t = ARM and the record after the arming row in the file, t being the last data timestamp before the record |

**Volatile parameter ignore list:** configurable in the rules file. Default list is confirmed against the golden logs; candidates are flight-time accumulators and per-flight identifiers.

No rule threshold is presented as correct for any aircraft.

A rule whose input data is missing or unreadable is FAIL, never N/A; N/A means only that the rule does not apply (R6 on a vehicle that is not VTOL, R7 without `[authorized_sources]`, R4 and R5 on a log with no armed flight). The overall status is FAIL when any rule is FAIL; else NO ARMED FLIGHT when R5 is N/A; else WARN when any rule is WARN; else PASS. The rules file starts with `format = "sfr-rules/1"`, and unknown keys are rejected. A topic, pattern, parameter name, command id, or source listed twice in one list is a rules file error. The baseline file is a QGroundControl `.params` export (tab-separated vehicle id, component id, name, value, type 6 int32 or 9 float32) plus one line `# Firmware: <version> [<git hash prefix>]`; float values compare after rounding to float32, as numbers (-0 equals 0, and any NaN, written `nan`, equals any NaN).

### B1.7 Record format (`.sfr`)

JSON, canonicalized with RFC 8785 (JSON Canonicalization Scheme) wherever bytes are hashed. The record contains no JSON floating-point numbers: unsigned 64-bit measurements (timestamps, sizes) are decimal strings; counts, sequence numbers, message indexes, and enumerated values (nav state, command id, MAVLink ids) are JSON integers, each below 2^53 by construction (a log yields at most 100,000 events); and parameter values are typed strings (`i32:5`, `f32:0.15`, float32 written as its shortest round-trip decimal in plain positional notation, with the digits ECMAScript `Number::toString` would choose: fewest digits, then the closest, an exact tie to the even digit; `f32:NaN` for any NaN, `f32:Infinity` and `f32:-Infinity`). A `.sfr` file is stored as its canonical bytes, and verify rejects any file that differs from the canonical form of its own parse.

Top-level fields: `schema_version` (`4`; schemas 1 to 3 are not accepted, see Compatibility rule); `tool` (`name`, `version`, `build_commit`); `seal` (`allow_ignore_all`, `allow_untested_version`, `time_utc` as `YYYY-MM-DDTHH:MM:SSZ`, `key_fingerprint`, `key_label`, `key_custody`, `crypto_crates` (each crate's `name` and crate `version`, sorted by name), `signer_certificate` and `certificate_chain` or null); `log` (file name, size, sha256, blake3, firmware, vehicle type with `vtol_type`, `vehicle_status_instances`, `skipped`); `config` (firmware, sorted parameter map, `watched_parameters`); `baseline` (firmware, parameter map, ignore list, the baseline file's `sha256`); `rules` (embedded rules text and its sha256); `results` (per rule: id, status PASS, WARN, FAIL or N/A, expected, found, detail); `sealed_topics` (the sealed topic digests of B1.5, sorted by topic, then `multi_id`; empty without `[sealed_topics]`); `events` (ordered list); `status` (PASS, WARN, FAIL or NO ARMED FLIGHT, computed from the results); `merkle` (algorithm, leaf count, root, and `sections`, the number of leaves in each section); `signature` (algorithm `ed25519`, value).

**Leaves**, in this fixed order: seal context (`schema_version`, `tool`, `seal` without the signature); log identity; config; baseline; rules; each result in rule-id order; each sealed topic digest in topic and `multi_id` order; each event in sequence order. Each leaf is hashed with a one-byte tag for its section (`0x01` seal context, `0x02` log, `0x03` config, `0x04` baseline, `0x05` rules, `0x06` result, `0x07` sealed topic digest, `0x08` event). Standalone verify checks each order; deep verify (`--ulog`) recomputes every digest and names a changed sealed topic by topic and instance.

**Key custody** is one of `pkcs11-token` (the private key never leaves a PKCS#11 token or HSM), `tpm-sealed` (the seed is sealed to one TPM 2.0 at rest and is in process memory for one signature), or `file-evaluation` (a key file; evaluation only). Custody is signed but declared by the sealer, and verify always reports it as declared (B1.9).

**Hashing:** leaf hash = SHA-256(0x00 || section tag || JCS(leaf)). Node hash = SHA-256(0x01 || left || right). Odd-node handling follows RFC 6962 (the left subtree holds the largest power of two below the leaf count; nothing is duplicated); `merkle.algorithm` is `sha256-rfc6962`, `merkle.root` and `signature.value` are lowercase hex. **Signed payload** = ASCII `SFR-RECORD-V1` || 0x00 || schema_version as 4-byte big-endian || tree size as 8-byte big-endian || the leaf count of each of the eight sections as 8-byte big-endian || Merkle root (122 bytes). Ed25519 signature over the signed payload.

**Keys:** `sfr.pub` is a PEM `PUBLIC KEY` (RFC 8410 SubjectPublicKeyInfo) and `sfr.key` a PEM `PRIVATE KEY` (PKCS#8 v1), the forms `openssl pkey` reads; `seal` also reads PKCS#8 v2 with the public key and no attributes, and refuses one whose public key does not match. The key fingerprint is `sha256:` and the lowercase hex SHA-256 of the SubjectPublicKeyInfo DER.

**Compatibility rule:** a verifier must reject a `schema_version` it does not know; it must never guess. `sfr` verifies schema 4 only: schemas 1 and 2 hashed leaves without a section tag and did not sign the tree size or section counts, so a leaf moved between sections left the root and signature valid; schema 3 results came from rules that read one `vehicle_status` instance and did not check field types; a log sealed under them is sealed again.

`docs/RECORD_FORMAT.md` documents the format exactly enough for an independent implementation, with copy-paste `openssl` and `b3sum` commands that verify the signature and the log digest without `sfr`.

### B1.8 Markdown report (`.sfr.md`)

Emitted by `seal` beside the record as `<name>.sfr.md`, rendered from the record bytes `seal` has just signed; `seal` writes the record and the report together or neither, never overwrites either, and its JSON output names both files (`record`, `report`). Renders in GitHub and GitLab; no table has more than five columns. Contents: under the title, the Merkle root and the key fingerprint, so a reader can compare them with what `sfr verify` prints; overall status; a rules table; parameter differences; a "Parameters changed in flight" table built only from the PARAM_CHANGED_IN_FLIGHT events, with a one-line note that they are reported, not a rule failure; a "Transition tuning" section when the vehicle is VTOL (the `vtol_type` and each watched parameter with baseline and flown values, marked MATCH, DIFF, or not compared when the baseline lacks it); a sealed topics table (topic, instance, message count, time span, digest prefix); an event timeline table with a category column for COMMAND events, and under it a one-line legend for the `initial` field (`docs/RECORD_FORMAT.md`) when an event carries it; log identity and digests; Merkle root, key fingerprint, key custody, crypto crates, and the exact `sfr verify` command, quoted so that POSIX sh, bash and PowerShell each read a file name as that file; when a name holds a character no quoting makes safe in all three (a control character, a character that hides text, or a single quote), the report says so, shows the name with markers, and gives lines that set shell variables from the name's bytes, then a command that uses the variables. A record sealed with a `file-evaluation` key starts with the line `EVALUATION KEY: not for operational use`. Generated only from the record, so it cannot say anything the record does not; every value from the record is written with a backslash before each ASCII punctuation character, which Markdown shows literally, so no value can form a link, an emphasis, an entity, or a table cell, and a character that hides or reorders text (a Unicode format character such as the bidirectional controls and the zero-width characters, or the line and paragraph separators) is written out as `<U+202E>`, so it shows; a control character (ESC, a newline, a tab) is written out the same way, as `<U+001B>`, never dropped or turned into a space. `sfr` writes the same markers for those characters, and for control characters, in everything it prints (a newline in a file name or log text included), and `--json` output writes them as `\uXXXX` escapes.

### B1.9 Threat model (`docs/THREAT_MODEL.md`, one page)

First paragraph, verbatim intent: *The signature binds the sealed record to the holder of the signing key at the moment of sealing. It proves the record and, with `--ulog`, the log have not changed since then. It does not prove the flight stack wrote a truthful log, that nothing happened to the log between disarm and sealing, or that the sealing machine was uncompromised.*

Then: sealing on the companion computer immediately after disarm (documented post-disarm hook example) shrinks the disarm-to-seal gap. A stolen key invalidates trust in every record signed with that fingerprint after the compromise. Operational seals use a key that never leaves a PKCS#11 token or HSM (`pkcs11-token`), or an Ed25519 seed sealed to the companion computer's TPM 2.0 (`tpm-sealed`: no other TPM can load it, and it is in `sfr`'s memory for one signature). File keys are evaluation-only, and every record and report sealed with one says so. Custody is signed but declared by the sealer, and `sfr` never reports it as proven. A signer certificate chain to the operator's trust anchor shows whom the CA issued the key's certificate to; custody rests on that CA's own policy (for example, certifying only keys it has seen held in hardware), which `sfr` cannot see. Revocation is checked against CRL files given to `verify`; there is no online revocation check, by design.

`docs/THREAT_MODEL.md` names the crypto crates, states that they have no CMVP certificate, and states that `sfr` makes no FIPS 140 claim. **Sealed topics.** The raw log digest already covers every topic. Sealed topic digests add a per-topic proof inside the record: standalone verify covers them without the log, and a future inclusion-proof export can disclose one topic's digest without revealing the rest of the record. They do not interpret, validate, or judge the topic's contents. **Command sources.** Command source ids are the values recorded in the log. MAVLink source ids are self-reported unless MAVLink message signing is enabled on the link. R7 proves which source the log recorded, not that the source was authentic. The record contains the full parameter set and is as sensitive as the log; handle it the same way.

### B1.10 Production-grade gates (all binary; all enforced in CI unless marked)

| Gate | Pass criterion |
|---|---|
| Static binaries | For the x86_64, aarch64, and armv7 (`armv7-unknown-linux-musleabihf`) musl builds of `sfr`, `readelf -lW` shows no INTERP program header and `readelf -dW` shows no NEEDED entry (static-pie is allowed on x86_64; `ldd` is not used because it misreports static-pie and foreign-architecture binaries); for armv7, `file` also reports a statically linked 32-bit ARM executable. `sfr-pkcs11-helper` is exempt and is the only dynamically linked artifact |
| Peak memory | The maximum resident set size of `seal` is measured and reported on x86_64 for every golden log and for the 100 MB benchmark log; if the 100 MB log needs more than 256 MB, the cause is reported before work continues (small companion boards commonly have 512 MB) |
| armv7 | The full test suite passes on armv7 under QEMU user-mode emulation in CI, built optimized with integer overflow checks and debug assertions on (Cargo profile `qemu-test`). This is a correctness gate only: no armv7 performance number is gated or published unless measured on real hardware. CI also seals every golden log on x86_64 and on armv7 and requires byte-identical records and reports (`scripts/check_same_records.sh`) |
| No network | Dependency tree contains no networking or async-runtime crates (CI check against a deny list); demo passes in `docker run --network=none`. | No unsafe | `#![forbid(unsafe_code)]` in all Inquiro crates |
| Deterministic | Same inputs plus `--seal-time` and key produce byte-identical `.sfr` and `.sfr.md`, across x86_64, aarch64, and the WASM build |
| Replay | `verify --ulog` on every golden log reproduces sealed results byte-for-byte |

| Exit codes | An integration test triggers each of codes 0 to 4 |
| Errors | Every error names the file, and where relevant the topic, field, or parameter; no panics on any input |
| Performance | Benchmark script reports seal time for 10, 50, and 100 MB logs and standalone verify time; gates: 100 MB seal under 2 s on x86_64 and under 4 s on real aarch64 hardware (not emulation); standalone verify under 10 ms for records up to 10,000 events, measured in-process (`sfr_core::verify` on the record bytes in memory) as the median of 101 runs on the CI runner (`crates/sfr/tests/verify_perf.rs`); the same test reports the end-to-end `sfr verify` time, which adds process start and reading the files, and that time is reported, not gated |
| Code quality | `rustfmt --check` clean; `clippy` with warnings as errors; all tests green |
| Supply chain | `cargo-deny` clean for licenses (no GPL, AGPL, or unknown) and advisories; CycloneDX SBOM per release. |

| Releases | Each release ships `SHA256SUMS` plus an Ed25519 signature over it, and the public release key in the README. Each release names its crypto crates and their crate versions. ### B1.11 Out of scope for v1
Onboard or in-flight sealing; C/C++ library or ROS2 node; MAVLink `.tlog` and ArduPilot DataFlash (the ingest layer sits behind a `FlightLogIngestor` trait so ArduPilot is a clean v2 addition); computer-vision events; HTML report; any server, upload, or fleet database; hardware key attestation (PIV attestation, TPM2_Certify); online revocation (OCSP); quantum-resistant signatures; inclusion-proof export (format supports it; command is v2); reason-coded waivers; multi-flight trends; compliance mappings.

### B1.12 Language rules for all docs and README
- No target company, aircraft, or customer names.
- No internal Inquiro codenames.
- No compliance claims (no "DoDD 3000.09 compliant" or similar).
- No number that a script in the repo does not produce.
- Name the version plainly (`sfr 0.1.0`), never "v1.0": the report, `seal --dry-run` and the docs use that one form.
- No FIPS, validated, or compliant claim anywhere: `sfr` uses no CMVP-validated module, and docs, output, and records describe its cryptography only by its crates and crate versions. IL4, IL5, and NIST SP 800-171 apply to whole systems and environments, never to a binary. Never write "FIPS compliant", "FIPS certified", "FIPS validated", or any compliant, certified, accredited, authorized, or validated status for `sfr`; `scripts/check_language.sh` fails CI on such wording.
- No em-dashes.
