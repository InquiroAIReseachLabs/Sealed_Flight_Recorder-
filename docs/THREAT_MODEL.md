# Threat model

The signature binds the sealed record to the holder of the signing key at the moment of sealing. It proves the record and, with `--ulog`, the log have not changed since then. It does not prove the flight stack wrote a truthful log, that nothing happened to the log between disarm and sealing, or that the sealing machine was uncompromised.

## What is signed

Only the record, `<name>.sfr`, is signed: the Ed25519 signature covers its Merkle root, and the root covers every field of the record (the format is in [RECORD_FORMAT.md](RECORD_FORMAT.md)). The report `<name>.sfr.md` is a readable view that `seal` renders from the record; it has no signature and no digest of its own. `sfr verify` binds it to the record: once the record verifies, it renders the report again from the record and requires the `.sfr.md` beside the record, or the one `--report` names, to be identical, byte for byte (rendering is deterministic and the same on every target). The report is required: with none beside the record and no `--report`, verification fails unless `--no-report` is given, so a forged report under another name never stands in for the record's. A report read without verifying its record proves nothing.

## What a seal proves

`sfr verify` reports `Integrity: VERIFIED` only after checking the signature against a public key the verifier supplied (`--pubkey`) or a key whose certificate chains to a trust anchor the verifier supplied (`--trust-anchor`), and only for a record that is not signed with an evaluation key (those need `--allow-evaluation-key`, else `Integrity: REFUSED`); given neither key nor anchor, it reports `Integrity: NOT CHECKED` and exits 4. A record so verified proves that it has not changed since it was sealed: that this record, signed by the key with this fingerprint, holds these rule results, this configuration and these events, and that its report, when one is beside it or named, is the one it renders; with `--ulog`, that they match these log bytes (SHA-256 and BLAKE3 of the whole file) and that the embedded rules and baseline give the same results from them. The format is in [RECORD_FORMAT.md](RECORD_FORMAT.md).

## What a seal does not prove

- **That the data was genuine or accurate before sealing.** The seal proves that nothing changed after sealing. It says nothing about the log before then.
- **That the log was honest.** `sfr` checks what the log says, not whether the flight stack, its sensors or its estimator told the truth.
- **That the vehicle did what the log says.** A log is the flight stack's account of the flight, not the flight.
- **That the key holder is who they claim.** The record names a key by fingerprint. How that key is held (`key_custody`) is the sealer's statement, a string the sealer wrote: a key file can say `pkcs11-token` as easily as a token can. `verify` therefore prints custody as `unattested (declared pkcs11-token)` unless the signer certificate (`seal --cert`, `--chain`) chains to a trust anchor the verifier supplied (`verify --trust-anchor`), and then as `attested by certificate chain to the trust anchor ...`. What that attests is only as much as the CA's issuing practice: `sfr` cannot see whether the CA issued the certificate because the key is held in hardware, so a CA that also issues certificates to file keys makes those keys attested too. Get the public key or the trust anchor from its owner by a channel you trust: `sfr verify` checks the signature against the key given with `--pubkey` or the key whose certificate chains to `--trust-anchor`, and given neither prints `Integrity: NOT CHECKED` and exits 4. A public key that came with the record proves nothing about who signed it.
- **When the log was made, or sealed.** `seal.time_utc` is a claim: the sealing machine's clock or the `--seal-time` given, signed but not proven, and `verify` labels it claimed. Only a trusted time supplied from outside the sealer would prove it; `sfr` takes none. What `verify` does with it: it never uses it to judge a certificate, and it refuses a claimed time later than the verification time (the verifier's clock, or `--at`) by more than 300 seconds of clock skew. A claimed time in the past stays unproven: a key holder can claim any earlier time, so the record says nothing about whether it existed then.
- **That nothing changed the log before sealing.** The window from disarm to seal is open; see below.

| Spoofed MAVLink source ids | **not detected**: R7 checks the ids the log recorded | command sources, below |

## Disarm to seal

Sealing on the companion computer immediately after disarm shrinks the window in which the log can be changed before it is sealed. [INTEGRATION_NOTES.md](INTEGRATION_NOTES.md) gives a post-disarm example.

## Keys

- **`pkcs11-token`:** the private key never leaves a PKCS#11 token or HSM; the token signs.
- **`tpm-sealed`:** the Ed25519 seed is sealed to one TPM 2.0 and no other TPM can load it. It is in `sfr`'s memory for one signature, then zeroized.
- **`file-evaluation`:** a key file, for evaluation only. Every record sealed with one records that custody, its report and `sfr verify` output start with EVALUATION KEY, and `sfr verify` refuses it (`Integrity: REFUSED`) unless given `--allow-evaluation-key`.

`seal` signs with all three: `--key-uri pkcs11:...` through `sfr-pkcs11-helper`, `--key-uri tpm-sealed:<dir>` through tpm2-tools, and `--key <sfr.key> --evaluation-only`. A stolen key invalidates trust in every record signed with that fingerprint after the compromise. Custody is signed into the record but declared by the sealer, and `verify` never prints it as established from that string: it prints `unattested (declared ...)`, or `attested by certificate chain to the trust anchor ...` when the signer certificate chains to an anchor the verifier supplied. `--require-hardware-key` means attested by such a chain, not declared (with `--pubkey` it always refuses), and a declared `file-evaluation` is refused by it whatever the chain. A certificate chain to the operator's trust anchor adds what that CA vouches for: if the CA certifies only keys it has seen held in hardware, its certificate is the operator's evidence of custody, but `sfr` cannot see that policy, and a CA that also certifies file keys makes those attested too. `verify --trust-anchor` requires the chain to reach the anchor, every certificate to be valid at the verification time (the verifier's clock, or the time given with `--at`; never the claimed seal time), the signer certificate to carry the sfr record-signing extended key usage (`2.25.182460915354635260549596502533646383540`) and keyUsage digitalSignature, and not also code signing, TLS server authentication or any usage, and no certificate in the path to be listed in the current CRL of its issuer, given with `--crl`. A listed certificate counts as revoked whatever its revocation date, because the seal time is the sealer's own statement and a stolen key could backdate a seal. Every CRL given is read, in any order, and for each issuer the one with the highest CRL number is current (RFC 5280 section 5.2.3), so an older CRL given first cannot hide a revocation. Every issuer in the chain needs a current CRL; a missing one, one past its `nextUpdate` by the verifier's clock, or one from another issuer, does not count, and `--no-crl-check` is the explicit, warned way to skip the check. There is no online revocation check, by design: a CRL is only as current as the file given, and withholding the newest CRL is not detected until its predecessor's `nextUpdate` passes.

`sfr` checks nothing about a token itself: not whether its private key can be exported, how it was made, or who has vouched for it. It needs a token that signs with Ed25519 (`CKM_EDDSA`); choosing one whose key cannot leave it is the operator's job. No shipping TPM implements EdDSA, so in `tpm-sealed` the TPM only protects the seed at rest: the seed is unsealed into `sfr`'s memory for one signature. A PCR policy (`keygen --tpm-sealed --tpm-pcrs`) makes the TPM refuse to unseal when the measured boot state differs, so after a firmware or boot change the key must be made again.

## Sealed topics

The raw log digest already covers every topic. Sealed topic digests (`[sealed_topics]` in the rules file) add a per-topic proof inside the record: standalone verify covers them without the log, and a future inclusion-proof export can disclose one topic's digest without revealing the rest of the record. They do not interpret or judge the topic's contents.

## Command sources

Command source ids are the values recorded in the log. MAVLink source ids are self-reported unless MAVLink message signing is enabled on the link. R7 proves which source the log recorded, not that the source was authentic.

## Cryptography

On every target, `sfr` computes SHA-256 with `sha2`, Ed25519 with `ed25519-dalek`, and the supplementary BLAKE3 digest of the raw log with `blake3`; `seal.crypto_crates` names each crate and its crate version. The same crates build every target, so a record is byte-identical wherever it is sealed. These crates have no CMVP certificate, and `sfr` makes no claim under any cryptographic module standard: treat its digests and signatures as made by ordinary open source code. `sfr` makes no claim that it meets any security standard or regime; such requirements apply to whole systems and how they are run.

## Sensitivity

The record contains the full parameter set and is as sensitive as the log; handle it the same way.
